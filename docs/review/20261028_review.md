- **Review date:** 2026-10-28

## How this review was produced

The review was run as a four-reviewer panel plus an adjudicating main reviewer:

1. **Security** — secret/key handling, local AEAD/HKDF design, redaction, OpenBao transport and destruction semantics, root-key decoding, supply chain.
2. **Go, API and architecture** — Go 1.27 idioms, package layout, facade/internal boundaries, public surface, value semantics, persistence and lifecycle.
3. **Testing and reliability** — conformance suites, failure injection, fuzzing, race/flake behaviour, coverage, CI gates, retries and timeouts.
4. **Developer experience, documentation and maintainability** — first-use path, examples, godoc, release/versioning, observability, bus factor and doc correctness.

Each reviewer read the full tree and ran cheap read-only checks. The main reviewer ran the authoritative gates on Go 1.27.3, reproduced the highest-risk claims with throwaway programs under `/tmp/opencode` (never committed), and reconciled disagreements. One subagent was retried after a transient DNS failure; all four panel reviews completed.

## Executive summary

**Verdict: NO — this module is not production grade today.**

The cryptographic core is thoughtful and the conformance suite is well above average, but the module is not yet safe to adopt as a production dependency. The five things that matter most are:

1. **OpenBao transport can disclose the token and plaintext DEKs (SEC-01).** The adapter accepts `http://`, follows redirects by default, and Go forwards `X-Vault-Token` and 307/308 request bodies to the redirect target. I reproduced both the token and the base64 plaintext DEK arriving at a second host.
2. **Crypto-shredding is not linearizable and tombstones are ignored on reads (SEC-02).** A `WrapDEK` that passes the tombstone check before a concurrent `DestroyKEK` can recreate the deleted transit key; `UnwrapDEK` then decrypts the resulting record because it never checks the tombstone. A deterministic fake-server probe returned a live DEK after destruction.
3. **The redaction guarantee is incomplete (SEC-03, SEC-04).** `KeyManager` redaction methods are pointer-receiver only, so `fmt.Sprintf("%v", *km)` prints the local wrapping key or OpenBao token. `Config` secrets are exported fields, so `encoding/xml`, `encoding/gob`, `%p` and third-party dumpers bypass the JSON/`fmt` redaction.
4. **The advertised default local adapter has no durable store (ARCH-01, DX-01).** The README quickstart uses `local.NewMemKEKStore()`; a reader who copies it loses every KEK — and all content — on restart. The only shipped store is explicitly test-only.
5. **The verification/operations layer is not production-ready (TEST-01/02/03, OPS-01/02).** There are no HTTP fault-injection tests, no fixed local wire-format fixture, no fuzzing and no durable-store integration test. The OpenBao adapter has no retry/backoff or typed transient errors, and the module exposes no logging/metrics/tracing hooks or lifecycle close.

What is already strong: the local AES-256-GCM/HKDF construction with per-record key derivation and AAD binding is sound; there is no `unsafe`, `reflect`-based secret handling or cgo; the shared conformance suite and named security subtests are a good foundation; `govulncheck` is clean; full cross-package coverage is 81.9% and `mise run check` passes once. Those strengths do not offset the blockers above.

## Findings

### Go best practices and API shape (GO)

#### GO-01 — `WrappedDEK` has no stable persistence or version contract
**Severity:** MAJOR  
**Evidence:** `internal/domain/keys.go:274-301` defines the persisted record as a struct with exported fields and no tags or format version; `README.md:43-45` tells callers to store it next to ciphertext; the former golden renderer included field names/types but dropped struct tags.

```go
type WrappedDEK struct {
	KEKID      KEKID
	KEKVersion KEKVersion
	KeyID      KeyID
	Ciphertext []byte
}
```

**Why it matters:** consumers will naturally `json.Marshal` this value, making default field names and base64 encoding an accidental storage schema. Adding/renaming a field or changing a tag later silently breaks stored rows, and an AST snapshot would not show tag changes because the renderer ignores tags. The type also has no adapter identifier, so records from different adapters look alike.

**Recommended change:** define an explicit persistence contract: either `MarshalBinary`/`UnmarshalBinary` with a version byte, or documented stable JSON tags plus a `Format`/`Adapter` field and migration rule. Include struct tags in the API golden renderer. This is additive if done with new methods; changing default JSON is behavioural and should be batched before v1.

**Breaking:** yes if the default encoding or fields change; additive if optional. **Effort:** M.

#### GO-02 — `RewrapDEK` is a mandatory method whose security guarantee only the transit adapter can meet
**Severity:** MAJOR  
**Evidence:** `keymanager/keymanager.go:144-155` says `RewrapDEK` “MUST NOT be implemented as unwrap followed by wrap” and that “the plaintext key never enters this process”; `keymanager/local/local.go:332-343` says the local adapter cannot offer that and decrypts the DEK in-process; `keyringtest/suite.go:593-602` only asserts that no plaintext is returned, not that it never entered the process.

**Why it matters:** a rotation job cannot tell from the interface whether it is safe to run with a decrypt-free token. The port makes an optional capability look universal, and the local adapter internally implements the forbidden shape while still passing the suite. Local rotation code is therefore safe only by accident of the caller not being trusted with plaintext.

**Recommended change:** expose the capability explicitly — e.g. an optional `interface{ RewrapDEKWithoutPlaintext(...) }` or a `Capabilities()` method — and test it per adapter. Alternatively, weaken the core contract and state that `RewrapDEK` may decrypt in-process when the adapter’s key material is local. Adding an optional interface is non-breaking; splitting `KeyManager` is breaking.

**Breaking:** no for an optional capability; yes if the port is split. **Effort:** M.

#### GO-03 — Several version/store invariants are unenforced at the boundary
**Severity:** MINOR  
**Evidence:** `internal/domain/keys.go:121-122` (`Next` is `v + 1` on `uint32`); `keymanager/local/local.go:421-422` uses it; `keymanager/local/store.go:104-106` only initializes the map in the constructor and `:126` panics on a zero-value `MemKEKStore`; `store.go:109-133` never validates `id` or `version`; `internal/domain/keys.go:307-321` only checks that ciphertext is non-empty, with no upper bound.

**Why it matters:** after `MaxUint32` rotations `Next` wraps to the invalid version 0, and a buggy persistent store returning 0 produces records that later fail `WrappedDEK.Validate`. `var store local.MemKEKStore` is a normal Go construction that panics on first write. Invalid IDs/versions can be stored by any direct `KEKStore` user, and an oversized caller-supplied ciphertext forces a large allocation or outbound request before authentication.

**Recommended change:** reject rotation at `math.MaxUint32`; validate `current`/`next` before storing and after reading from a store; validate IDs/versions in `KEKStore.CreateKEKVersion`; lazily initialize `MemKEKStore`; add a documented `MaxCiphertextLen` (local records are fixed at `headerLen + 32 + 16`) and reject larger records. Add tests for all of these.

**Breaking:** no signature change; invalid inputs that were previously accepted will now fail. **Effort:** S.

#### GO-04 — Manager lifecycle and defensive contracts are incomplete
**Severity:** MINOR  
**Evidence:** `keymanager/keymanager.go:58-198` defines six methods and no `Close`; `keymanager/local/local.go:175-180` retains the derived `wrapKey` indefinitely; `keymanager/openbaotransit/openbaotransit.go:188-197` retains the token and client; `keymanager/local/local.go` lacks the `var _ keymanager.KeyManager = (*KeyManager)(nil)` compile assertion that both other adapters have (`openbaotransit.go:918-919`, `externalkms.go:103-106`); `internal/domain/keys.go:177-181` says `Bytes` returns nil after destruction, but a value copy taken before `Destroy` still returns a non-nil 32-byte zero slice (verified).

**Why it matters:** the local adapter cannot zeroize its derived root-wrapping key at shutdown, and adding `Close` to `KeyManager` later would break every adapter/consumer. A caller using `Bytes() == nil` to detect destruction can be misled by a copy and pass an all-zero key to a cipher; `Validate` catches it, but direct `Bytes` use does not.

**Recommended change:** define an optional `interface{ Close() error }` (do not add it to `KeyManager` yet) and implement it on both adapters; document the transit token’s immutability. Add the local compile assertion. Keep destruction state in a shared pointer so every copy observes nil, or change `Bytes` semantics and test the copy case.

**Breaking:** optional interface is additive; changing `Bytes` semantics is behavioural. **Effort:** M.

#### GO-05 — Go 1.27 modernization opportunities are outstanding
**Severity:** NIT  
**Evidence:** `go fix -diff ./...` under Go 1.27.3 reports only three hunks: replace `Add`/`go`/`defer Done` with `sync.WaitGroup.Go` in `keyringtest/kekstore.go:267-274` and `keyringtest/suite.go:1218-1238`; replace the `saysAny` loop with `return slices.ContainsFunc(substrings, e.says)` in `keymanager/openbaotransit/openbaotransit.go:769-776`.

**Why it matters:** the module now requires Go 1.27.3; `WaitGroup.Go` removes an Add/Done mismatch class from concurrent tests, and `slices.ContainsFunc` is clearer. These are not defects, but leaving `go fix` suggestions unapplied makes the newer toolchain buy less than it should.

**Recommended change:** apply `go fix ./...`, then gofumpt/lint/test. The changes are mechanical.

**Breaking:** no. **Effort:** S.

#### GO-06 — Public godoc points adapter authors at unimportable `internal/domain` types
**Severity:** NIT  
**Evidence:** `keymanager/keymanager.go:44-48` says a caller mints a DEK with `domain.NewDEK`; interface signatures at `:59-198` use `domain.KEKID`, `domain.KeyID`, `domain.DEK`, `domain.WrappedDEK`; `keyringtest/suite.go:27-33` shows a test wrapper but not how to implement an adapter. The root aliases in `keyring.go:45-64` are the importable names.

**Why it matters:** CHARTER explicitly anticipates consumer-written adapters, but pkg.go.dev readers see an internal package they cannot import and must discover the alias trick. This raises the cost of the “write your own KMS adapter” adoption path.

**Recommended change:** add a compilable adapter-author example using `keyring.KEKID` etc.; change `domain.NewDEK` references to `keyring.NewDEK`; or move the port to a public package (breaking).

**Breaking:** docs/example no; moving the interface yes. **Effort:** M.

### Code cleanliness (CL)

#### CL-01 — The key-manager conformance suite is one 1,178-line function with duplicated tables
**Severity:** MINOR  
**Evidence:** `keyringtest/suite.go:70-1247` is a single `RunKeyManagerSuite` function; `:674-762`, `:769-866` and `:1091-1166` repeat overlapping mutate/error tables for rewrap, unwrap and invalid input.

**Why it matters:** the suite is the authoritative contract but is hard to review as one unit; reviewers cannot see which invariant a change affects, and a new adapter author must navigate a wall of subtests. Duplicated cases drift when one table is updated and another is not.

**Recommended change:** split the suite into per-invariant files/functions (`roundtrip_test`, `rotation_test`, `forgery_test`, `redaction_test`, etc.) or at least into named helper functions; extract shared case builders for “mutate a valid record” and “expected sentinels”. No public API change.

**Breaking:** no. **Effort:** M.

#### CL-02 — Dead or unwired verification mechanisms remain in the tree
**Severity:** MINOR  
**Evidence:** `keyringtest/redaction.go:191-217` exports `RendersOnlyARedactionMarker`/`unmarkedRenderings`, but there are no callers and coverage is 0%; `CONVENTIONS.md:542-554` claims `redactlint` enforces missing redaction interfaces, but there is no dependency, custom linter or CI invocation; `.golangci.yml:28-44` denies OTel metric imports on behalf of `internal/obs`, which does not exist in this module.

**Why it matters:** the module advertises a second enforcement mechanism that is not wired, and carries a dead public helper plus copied lint policy. This gives a false sense of coverage and makes the public surface larger than the module needs.

**Recommended change:** either wire `redactlint` as a custom linter/CI job and add a self-test for `RendersOnlyARedactionMarker`, or remove the claim/helper; prune the `internal/obs` depguard rules or replace them with a rule that applies to this module.

**Breaking:** removing an exported helper is breaking; pre-1.0 is the time. **Effort:** S.

#### CL-03 — Rationale is carried in very long comments and external references rather than a design document
**Severity:** NIT  
**Evidence:** `keymanager/keymanager.go:1-199`, `keymanager/local/local.go:1-39`, `keymanager/openbaotransit/openbaotransit.go:1-78` and `keyringtest/suite.go:1-33` contain long narrative comments, many citing “CAS design §8.x” or `kgs/docs/...` that are not in this repository. `README.md:87-89` listed only CHARTER, SECURITY and the former AST snapshot.

**Why it matters:** the comments are thoughtful, but the most important design rationale is not discoverable by an external adopter, and the code becomes harder to scan. When the external document changes, the comments drift.

**Recommended change:** move the envelope-encryption, threat-model, rotation and adapter-choice rationale into `docs/architecture.md` or ADRs, leave short “why” comments at the code, and link the docs from README.

**Breaking:** no. **Effort:** M.

### Architecture and internal consistency (ARCH)

#### ARCH-01 — No durable `KEKStore` ships; the default local adapter is not production-safe
**Severity:** BLOCKER  
**Evidence:** `README.md:28-31` uses `Store: local.NewMemKEKStore()` in the first example; `keymanager/local/store.go:77-85` says the in-memory store is wrong for anything persisted and its failure mode is “permanently unreadable”; `keymanager/local/local.go:125-130` says `Store` has no in-memory default because that is the “permanent loss of every encrypted byte” failure mode; the only implementation in the repo is `MemKEKStore` (`store.go:77-204`), while `keyringtest.RunKEKStoreSuite` (`keyringtest/kekstore.go:38`) is only a contract.

**Why it matters:** a newcomer copy-pastes the first example, persists ciphertext, restarts, and loses every KEK and all content. The module’s stated default adapter therefore cannot be used for its stated purpose without an implementation the module does not provide. This is the largest adoption blocker after the security issues.

**Recommended change:** ship a durable reference `KEKStore` (Postgres is the design’s stated target) with migrations and an integration test, or separate it into a companion module and make the local adapter explicitly “bring your own durable store”. At minimum, replace the README example with a named durable-store placeholder and a prominent warning; never show `MemKEKStore` next to “store the wrapped DEK”.

**Breaking:** no API change; adoption/docs change. **Effort:** L.

#### ARCH-02 — The `KEKStore` port lives inside the `local` adapter, coupling every store and the test suite to one adapter
**Severity:** MAJOR  
**Evidence:** `keymanager/local/store.go:23-75` defines `KEKStore` and `ErrKEKVersionExists`; `keyringtest/kekstore.go:38` declares `RunKEKStoreSuite(..., newStore func(t *testing.T) local.KEKStore)`; `keymanager/externalkms/externalkms.go:22-26` says the external adapter will need “the same store the local adapter uses.”

**Why it matters:** a Postgres implementation must import `local` to implement a core persistence port; `keyringtest` (a non-test package) drags `local` into every consumer’s graph; and a future external-KMS adapter is forced to depend on `local` or duplicate the interface. The dependency direction is inverted for a port that outlives the adapter.

**Recommended change:** move `KEKStore`, `MemKEKStore` and `ErrKEKVersionExists` to a neutral package (e.g. `keymanager/kekstore`), alias them from `local` for a transition, and have `keyringtest`/`externalkms` use the neutral package. `apidiff` reports the import-path change.

**Breaking:** import-path change; aliases can soften it. **Effort:** M.

#### ARCH-03 — “Swapping local for transit changes nothing else” is false for persisted records and does not explain migration
**Severity:** MAJOR  
**Evidence:** `README.md:48-49` says swapping the adapter changes “the import and the config, and nothing else”; `keymanager/local/local.go:9-14` makes a similar claim; `internal/domain/keys.go:296-300` says the opposite: “a record written by one adapter is not portable to another”; `keymanager/openbaotransit/openbaotransit.go:817-839` rejects non-transit ciphertext before any request.

**Why it matters:** every persisted `WrappedDEK` is adapter-specific. Switching local to transit makes all existing records unreadable unless the operator runs an unwrap-with-old/wrap-with-new sweep, and there is no migration helper or documented procedure. The sentence invites an outage during an adapter change.

**Recommended change:** reword the claim to “same call sites; existing records require a rewrap migration”; document or ship a tested side-by-side migration (old adapter unwraps, new adapter wraps). Add an adapter identifier/format field to the record if mixed storage is expected.

**Breaking:** docs-only for the wording; adding a record field is breaking. **Effort:** M.

#### ARCH-04 — The external-KMS adapter is a public stub with an incomplete configuration
**Severity:** MINOR  
**Evidence:** `keymanager/externalkms/externalkms.go:1-35` describes BYOK/HYOK and a cache/version-mapping design; `:45-59` defines only `Provider` and `KeyURI`; `:69-71` always returns `ErrNotImplemented`; the former AST snapshot pinned the stub as public API, and `keyring.go:96-97` re-exported `ErrNotImplemented`.

**Why it matters:** adopters can import and wire a package that can never work, and the future implementation will need `Store`, `CacheTTL`, token/credential source and provider-specific config — all of which will change the public surface. The `KeyURI` may contain a PKCS#11 PIN, yet `Config` has no redaction methods.

**Recommended change:** remove the package from the public API until a transport exists, or move it under `internal/`/an explicitly provisional package. If it must stay, add the required fields now, redact `KeyURI`, and document the stub as non-functional.

**Breaking:** removing a public package is breaking; pre-1.0 is the right time. **Effort:** S/M.

#### ARCH-05 — Key lifecycle/version management is incomplete and the local mutex serializes unrelated tenants
**Severity:** MINOR  
**Evidence:** `keymanager/keymanager.go:170-198` exposes rotation and whole-KEK destruction but no “current version” query, listing, or per-version retirement; `keymanager/local/local.go:185-191` has one process-global `mu`, held across store I/O in `RotateKEK` (`:411-412`), `DestroyKEK` (`:448-449`) and `currentOrCreatedVersion` (`:470-471`).

**Why it matters:** old KEK versions accumulate forever after lazy rewrap, with no way to retire a version once all records are migrated; operators cannot observe which version is current. A slow store call for tenant A blocks KEK creation/rotation/destruction for every tenant, and context cancellation can wait on the mutex.

**Recommended change:** add `CurrentKEKVersion`/`ListKEKVersions` and, if storage matters, a safe `RetireKEKVersion` API with a “no records remain” precondition; use per-KEK keyed locks or rely on the store’s `ErrKEKVersionExists` and keep I/O outside critical sections. Add tests for concurrent cross-tenant operations.

**Breaking:** additive methods are non-breaking; splitting lifecycle semantics may be breaking. **Effort:** M.

### Security (SEC)

#### SEC-01 — OpenBao redirects and plain HTTP leak the token and plaintext DEKs
**Severity:** BLOCKER  
**Evidence:** `keymanager/openbaotransit/openbaotransit.go:223-225` accepts both `http` and `https`; `:237-240` creates `&http.Client{Timeout: DefaultTimeout}` with no `CheckRedirect`; `:669` sets `X-Vault-Token`; `:674` calls `client.Do`; `:714` allows `Plaintext []byte` in request bodies. A throwaway `httptest` probe with a 307 redirect showed the collector receiving:

```
path=/v1/transit/encrypt/kek-victim
X-Vault-Token: s.super-secret-token
body={"plaintext":"p8xM+KFkEuhTfFYAcBR7oFAr2G+5dd9Ps3fsceWJfyE=","context":"a2V5LTE="}
```

**Why it matters:** Go’s default redirect logic forwards custom headers such as `X-Vault-Token` across hosts and 307/308 replay the body. A compromised/misconfigured proxy, an open redirect or an `http://` MITM obtains the OpenBao token and, for `WrapDEK`, the base64 plaintext DEK. This defeats the module’s core secret-handling guarantee.

**Recommended change:** reject `http` unless an explicit opt-in (preferably loopback-only) is configured; clone the caller’s client and install a `CheckRedirect` that refuses redirects (or permits only the same origin and never downgrades). Do not mutate a caller-owned `HTTPClient`; document the override. Add redirect/TLS tests.

**Breaking:** yes for deployments using HTTP or redirecting proxies; security fix. **Effort:** S.

#### SEC-02 — Crypto-shredding is not linearizable; reads ignore the tombstone
**Severity:** BLOCKER  
**Evidence:** `keymanager/openbaotransit/openbaotransit.go:259-282` checks `refuseIfDestroyed` once and then calls `cryptoCall`; `:288-321` does the same for `GenerateDEK`; `:447-491` writes the tombstone, raises `min_decryption_version`, then deletes; `:502-538` creates a missing key and retries; `:324-348` `UnwrapDEK`, `:359-374` `RewrapDEK` and `:380-398` `RotateKEK` never call `isDestroyed`. A deterministic fake-server probe returned:

```
WrapDEK err=<nil>, ciphertext="vault:v1:AAAA"
tombstone_exists=true UnwrapDEK err=<nil>, returned_material=true
```

**Why it matters:** if destroy completes between the tombstone check and the encrypt, transit’s upsert (or `createKEKIfMissing`) recreates a fresh key under the destroyed name. The returned record then decrypts because reads never consult the tombstone. A partial destroy — tombstone written, config or delete failed — also leaves a key that still unwraps, rewraps and rotates while the module reports a destroyed KEK. This makes an erasure certificate potentially false.

**Recommended change:** make the tombstone authoritative on every operation. Re-check it after a successful encrypt/datakey; if present, delete the recreated key (including `deletion_allowed`) and return `ErrKEKDestroyed`. Check it in `UnwrapDEK`, `RewrapDEK` and `RotateKEK`; cache positive results only, never negatives. For a strict guarantee, serialize wrap/create/destroy with a server-side lock or CAS marker, and document the linearization point. Add barrier and partial-failure tests.

**Breaking:** no API change; in-flight operations now fail correctly. **Effort:** L.

#### SEC-03 — `KeyManager` redaction is bypassed by value copies
**Severity:** BLOCKER  
**Evidence:** `keymanager/local/local.go:712-731` implements `String`, `Format`, `MarshalJSON` and `LogValue` on `*KeyManager`; the secret is `wrapKey []byte` at `:175-180`; `keymanager/openbaotransit/openbaotransit.go:924-944` does the same for `token` at `:194`. Tests pass only the pointer (`keymanager/local/local_test.go:425-430`, `keymanager/openbaotransit/openbaotransit_test.go:280-293`). A throwaway probe produced:

```
local pointer %v: local.KeyManager{wrapKey: [REDACTED], store: *local.MemKEKStore}
local value   %v: {[242 140 60 ... 9 57 197] 0x...}
bao value     %v: {https://openbao.invalid:8200 transit s.super-secret-token 0x...}
```

**Why it matters:** a value copy does not implement the four interfaces. `fmt.Sprintf("%v", *km)` or `slog.Any("km", *km)` reflects the unexported fields and prints the derived AES wrapping key or the OpenBao token. This is exactly the “redaction is not inherited through an unexported field” failure the conventions warn about, in the type that holds the module’s most valuable secret.

**Recommended change:** make redaction value-safe. For the transit manager, use value receivers (no mutex). For the local manager, move the mutex/state behind a pointer field (`state *keyManagerState`) and implement the four methods on the outer value type. Add tests for `km`, `*km`, a struct containing the value, and `slog.TextHandler`/`JSONHandler` with the value. Consider returning an opaque interface from `Open` if value copies should be impossible.

**Breaking:** internal layout change; public method set may change. **Effort:** M.

#### SEC-04 — `Config` secrets are exported fields, so XML/gob/`%p` and third-party serializers bypass redaction
**Severity:** MAJOR  
**Evidence:** `keymanager/local/local.go:105-123` exports `RootKey []byte`; `keymanager/openbaotransit/openbaotransit.go:137-155` exports `Token string`; redaction exists only for `String`/`Format`/`MarshalJSON`/`LogValue` (`local.go:144-170`, `openbaotransit.go:158-184`). A probe confirmed `encoding/xml` and `encoding/gob` emit the OpenBao token verbatim; `%p` on a `DEK`, `local.Config` and a `local.KeyManager` value prints the key bytes (see also SEC-03). `keyringtest/redaction.go:140-143` deliberately excludes `%p`.

**Why it matters:** a diagnostics endpoint, YAML/spew dump, XML/gob encoding or a `%p` in a log line leaks the deployment root key or OpenBao token despite the README’s “every rendering path” claim. The redaction convention says every type that transitively holds material implements the four interfaces; here the fields are exported, so encoders do not need those interfaces at all.

**Recommended change:** make secret fields unexported behind a `Secret` type, or implement `MarshalXML`, `GobEncode`, `MarshalYAML` (and the corresponding unmarshalers) to redact/refuse. For `%p`, hold the secret behind a pointer field so the bad-verb path prints an address, or document the remaining hole and remove the “every rendering” claim. Add tests for XML/gob and value/pointer paths. Unexporting fields is breaking; adding methods is not.

**Breaking:** yes if fields are unexported; no if only methods are added. **Effort:** M.

#### SEC-05 — `RootKeyFile` decoding can silently use a different key, and key material is copied into unzeroizable strings
**Severity:** MAJOR  
**Evidence:** `keymanager/local/local.go:662-679` tries hex, four base64 variants, then raw bytes if `len(contents) >= MinRootKeyLen`; the raw fallback uses untrimmed `contents`; `:665,671` convert the key file to `string` for `hex.DecodeString`/`DecodeString`; `:641,647,649` include the `RootKeyFile` path in errors although `Config.String` redacts it (`:144-147`). A probe confirmed `local.Open` succeeds with a 63-character truncated hex key (decoded as 47-byte base64), a 42-character text file (accepted raw), and a full hex key. The doc at `:658-661` says a short text file is not mistaken for a raw key, but does not address malformed text of 32+ bytes.

**Why it matters:** a typo, truncation, wrapped newline or a file written with the “wrong” encoder starts the service under a different key instead of returning `ErrInvalidConfig`; existing records then fail with `ErrUnwrapFailed`, and new data is encrypted under the wrong key. Converting key bytes to `string` creates immutable heap copies that cannot be cleared, contradicting the zeroization story. The path leak contradicts the config-redaction policy.

**Recommended change:** require an explicit encoding (`RootKeyEncoding` enum or a format prefix), use strict decoders that reject internal whitespace/newlines, and refuse ambiguous inputs instead of falling through to raw. Decode with `hex.Decode(dst, src)` and `encoding.Decode(dst, src)` on `[]byte`; clear failed candidates and the root clone on every error path. Omit the full `RootKeyFile` path from errors or use a basename. Add corruption/truncation tests.

**Breaking:** yes for deployments relying on auto-detection; make strict mode explicit. **Effort:** M.

#### SEC-06 — OpenBao tombstones are unauthenticated transit keys and can be forged by a create-capable token
**Severity:** MAJOR  
**Evidence:** `keymanager/openbaotransit/openbaotransit.go:602-612` treats existence of `keys/destroyed-kek-<id>` as destruction; `:455-470` returns nil when the real key is missing but a tombstone exists; `:62-67` documents a token policy with create on `keys/*`; `:617-622` creates the tombstone as an ordinary transit key.

**Why it matters:** anyone with the adapter’s create capability (a compromised application token or an operator using the mount directly) can create `destroyed-kek-x`, after which `DestroyKEK("x")` returns nil for a KEK that never existed — a false erasure certificate — and future wraps fail permanently. The same token can set `deletion_allowed` and delete a tombstone, allowing later resurrection. The tombstone carries no MAC, ownership marker or audit link.

**Recommended change:** store destruction records in an authenticated place (KV entry MACed with a separate key, or a database/audit store) and protect them from deletion by the application token. Split capabilities: create/wrap and destroy/config should not be the same credential. If transit keys must be used, add an authenticated marker value and verify it. Document the threat model for a compromised token.

**Breaking:** operational/config change; no Go API break. **Effort:** L.

#### SEC-07 — OpenBao error classification depends on English substrings and returns unbounded server text
**Severity:** MINOR  
**Evidence:** `keymanager/openbaotransit/openbaotransit.go:570-585` maps only six substrings to `ErrUnwrapFailed`; `:758-765` is a case-sensitive `strings.Contains`; the default branch returns the raw `apiError` including server messages; `:746-752` joins messages with no length cap. The reproduced 500 included an internal archive path and a large key-material blob.

**Why it matters:** OpenBao message text is not a stable API. A wording change can bypass the deliberately opaque sentinel and expose which check failed, turning the key manager into an oracle; server-controlled text can also contain control characters for log injection or flood logs. The package doc claims no error contains key material, but it cannot control what a server echoes.

**Recommended change:** classify by HTTP status/structured code where possible; default every decrypt/rewrap failure against an existing key to `ErrUnwrapFailed`; log detailed server text locally (sanitized/capped) and do not include arbitrary server text in returned errors. Add alternate-message and oversized-error tests.

**Breaking:** no API change; behavior change. **Effort:** M.

#### SEC-08 — The local AAD does not bind the record format version, and identifier validation permits Unicode bidi controls
**Severity:** MINOR  
**Evidence:** `keymanager/local/local.go:539-551` writes `record[0] = WrapFormatVersion` but the AEAD authenticates only AAD from `dekAAD`/`kekAAD` (`:600-619`); `openRecord` checks the version byte before authentication (`:557-563`). `internal/domain/keys.go:396-400` rejects `unicode.IsControl`/`IsSpace` but allows `Cf`/bidi controls such as RLO and zero-width joiners.

**Why it matters:** the version byte is unauthenticated metadata; today only `0x01` is accepted, so tampering fails closed, but a future v2 parser could accept a v1 record under different semantics. Tenant-controlled KEK/key IDs can visually spoof log or audit lines with bidi formatting characters.

**Recommended change:** include the format version in the AAD in a v2 format and support v1 read-only during migration. Reject `unicode.Cf`/bidi controls or restrict identifiers to a conservative ASCII subset in a reviewed change. Add tests.

**Breaking:** AAD change is wire-breaking for v1 records; bidi rejection may break exotic IDs. **Effort:** M.

#### SEC-09 — The module’s crypto-shredding and “root key outside the process” claims overstate what the adapters deliver
**Severity:** MINOR  
**Evidence:** `README.md:6` headlines “root key outside the process”, but `keymanager/local/local.go:9-14` explicitly keeps the root key in-process; `internal/domain/errors.go:45-56` and `keymanager/keymanager.go:183-197` say destroyed KEKs make content “permanently unreadable in every backup, archive tier and object-store version”, but deleting the wrapped KEK from the live store does not erase snapshots; `keymanager/openbaotransit/openbaotransit.go:1-8` says every wrap/unwrap lands in OpenBao’s audit log, which depends on audit devices being configured; `SECURITY.md:16-23` says the suite proves enforcement that belongs outside the process.

**Why it matters:** a deployment may choose local believing the root key is outside the process, or claim crypto-shredding while a database snapshot and the root key can restore the KEK. Audit-log claims create compliance expectations the adapter cannot enforce. These are security-boundary decisions, not wording nits.

**Recommended change:** scope the headline to transit/external KMS; state the local threat model explicitly; define crypto-shredding as “unreadable in the live system and its replicas configured for hard deletion, assuming backups and the root key are also handled”; state that audit logging requires OpenBao audit devices. Add this to SECURITY.md and the package docs.

**Breaking:** no. **Effort:** S.

## Cross-cutting themes

1. **Security claims outrun the implementation.** Redaction is pointer/`fmt`/JSON/slog-specific, while `%p`, XML/gob, dereferenced managers and exported config fields leak; “root key outside the process” is false for local; “permanently unreadable in every backup” is false if a snapshot and the root key survive; “every wrap/unwrap in the audit log” depends on server configuration.
2. **The production persistence/operations layer is missing.** There is no durable `KEKStore`, no retry/backoff, no observability hooks and no `Close`. The module is a good library core with a test-only default path, not yet a deployable key manager.
3. **The test suite is strong on sequential contract and forgery, weak on concurrency and failure.** It has excellent round-trip, ownership, tamper and redaction tests, but no HTTP fault injection, no linearizability/barrier tests, no local wire-format golden, no fuzzing and no durable-store integration. The one reproducible OpenBao 500 is in the untested layer.
4. **Tooling/docs drift after the Go 1.27.3 bump.** mise is the declared source of truth, but CI still hardcodes gofumpt/golangci-lint, README/CONVENTIONS still say Go 1.25.6, generated headers say `audit`, and the new gofumpt reformatted a file (now applied). The gate itself can fail open (`go list` error, missing gofumpt).
5. **Premature or mislocated public surface.** `KEKStore` lives in `local`, `WrappedDEK` has no persistence contract, `RewrapDEK` advertises a capability only transit provides, and the external-KMS stub is public while incomplete.
6. **Error handling is opaque where it should be and verbose where it should not be.** Sentinel errors are a good design, but classification depends on English substrings, unknown server messages escape, there are no transient/auth/rate-limit categories, and unbounded server text can flood logs or create an oracle.

## Open questions for the maintainer

These questions were answered by the maintainer on 2026-10-28; the decisions are recorded in “Maintainer decisions” below and should be treated as planning inputs.

### Q1. Is `local` a supported production adapter, or is production transit/external-KMS only?
**Context:** README calls local the default and uses `MemKEKStore`, but no durable store ships; `MemKEKStore` is explicitly test-only, and local keeps the root key in-process. Transit keeps the root key outside the process and needs no local store.
**Why it shapes work:** if local is production, ARCH-01 is a blocker and requires a durable reference store, restart tests and security docs. If not, the README must say local is for tests/single-process only, and the quickstart should use transit.
**Options:** (A) transit/external KMS only for production; local test/single-process. (B) make local production with a shipped durable store. (C) local production with a documented “bring your own durable store” contract.
**Recommendation:** **(B)** if single-binary/on-prem is a target; otherwise **(A)** and demote local explicitly. Do not leave the current mixed message.

### Q2. What is the threat model — what is trusted?
**Context:** The module handles root keys, transit tokens and DEKs; it currently trusts the OpenBao server/TLS, the KEK store and the process, but the docs do not say so. This decides redirect/TLS policy, zeroization expectations, tombstone design and whether a compromised server is in scope.
**Why it shapes work:** SEC-01/02/06 and SEC-04/05 cannot be scoped without it; “defend against a compromised OpenBao” implies a very different design (TLS pinning, key commitment, authenticated tombstones) than “trust the server and protect the store/caller logs”.
**Options:** (A) trust OpenBao/TLS and process memory; protect store theft, caller logs and network MITM. (B) zero-trust server: defend against a compromised/malicious key manager. (C) defend against a compromised host (process memory/core dumps).
**Recommendation:** **(A)** as the documented baseline, with explicit out-of-scope statements; add B/C only if a real consumer requires them.

### Q3. What exactly must crypto-shredding guarantee?
**Context:** `DestroyKEK` currently deletes the live key and writes a tombstone, but reads ignore the tombstone, a wrap race can recreate the key, and backups/snapshots may still contain the wrapped KEK. The docs claim “permanently unreadable in every backup”.
**Why it shapes work:** SEC-02/SEC-06 and TEST-03 depend on whether destroy must be linearizable against concurrent wraps/reads and whether backup restoration is in scope.
**Options:** (A) linearizable in the live system; backups and the root key are explicitly out of scope and documented. (B) best-effort tombstone, no linearizability claim. (C) transactional/coordinated deletion across store, server and backup lifecycle.
**Recommendation:** **(A)** now: make reads/writes tombstone-aware and linearizable in the live system, document the backup/root-key caveat, and add a barrier test.

### Q4. Should the durable `KEKStore` live in this module or a companion module?
**Context:** A production local adapter needs a persistent store; Postgres is the design target. The main module is currently stdlib-only, and testcontainers is already the only test dependency.
**Why it shapes work:** putting `pgx` in the core module burdens every consumer; a companion module adds a second `go get`/release. ARCH-01/ARCH-02 and TEST-05 depend on this.
**Options:** (A) add a Postgres store subpackage to this module. (B) create `github.com/laenenai/keyring-postgres` (or similar) with the store and integration tests. (C) keep only the port and require consumers to implement it.
**Recommendation:** **(B)** to keep the core dependency-light while still shipping a reference implementation; if single-binary adoption is the priority, **(A)** is acceptable.

### Q5. Are `WrappedDEK` records adapter-portable, or explicitly adapter-specific?
**Context:** `WrappedDEK.Ciphertext` is opaque and adapter-specific; the README currently implies adapter swapping is transparent. Consumers need to know whether one storage column can hold records from multiple adapters during migration.
**Why it shapes work:** GO-01 (persistence format), ARCH-03 (migration) and the record schema depend on this. A portable envelope needs an adapter/format field and a common ciphertext; adapter-specific records need a migration tool.
**Options:** (A) adapter-specific records with an `Adapter`/`Format` field and a documented side-by-side migration. (B) portable envelope with a common wrapper format. (C) separate record types per adapter.
**Recommendation:** **(A)** — explicit adapter identity plus migration tooling is simpler and honest. Revisit portability only if mixed-backend storage is a real requirement.

### Q6. When does the API freeze and what does v1 promise?
**Context:** The module is pre-1.0 with tags v0.1.0/v0.2.0; breaking changes are still cheap, and several P0/P1 fixes will change signatures or behavior (Config fields, `KeyManager` redaction/value semantics, maybe `KEKStore` location).
**Why it shapes work:** it determines whether now is the time to batch all breaking changes, and what support/compatibility external adopters can expect.
**Options:** (A) batch the P0/P1 breaking changes and cut v1.0.0. (B) stay v0.x with documented breaking changes per minor. (C) stabilize the core and keep adapters/stores in separate unstable modules.
**Recommendation:** **(A)** after the P0/P1 work, with a CHANGELOG and semver policy; or **(C)** if adapters need independent cadence.

### Q7. Which OpenBao/Vault versions are supported?
**Context:** The adapter is tested only against `openbao/openbao:2.2.1` but claims Vault wire compatibility; error classification depends on English messages, so version differences matter.
**Why it shapes work:** TEST-01/07 and OPS-01 depend on whether a Vault/newer-OpenBao matrix is required; the docs must qualify the claim either way.
**Options:** (A) support OpenBao 2.2.x only, pin and document it. (B) support OpenBao + Vault with a CI matrix. (C) define a generic transit-compatible contract and test a representative set.
**Recommendation:** **(A)** now, **(B)** when a consumer needs Vault; do not claim Vault compatibility without a matrix.

### Q8. Should the external-KMS package remain in the public API?
**Context:** It always returns `ErrNotImplemented`, its config lacks the store/cache/credential fields its own docs require, and it increases the public and compatibility surface.
**Why it shapes work:** ARCH-04 is a remove-or-complete decision; implementing it requires a durable store and provider transports, which is a large scope.
**Options:** (A) remove it from the public API until implemented. (B) keep it internal/provisional. (C) implement one provider (AWS KMS) first.
**Recommendation:** **(A)** remove it now; pre-1.0 is the time, and it reduces the surface. Reintroduce with a real transport and tests.

### Q9. Should OpenBao operations retry automatically, and which ones?
**Context:** A transient 500/429/network error currently becomes opaque; a retry of `RotateKEK` can create an extra version, and a retry of `GenerateDEK` can discard a generated key.
**Why it shapes work:** OPS-01/TEST-01 and the error taxonomy depend on it; callers need to know whether `errors.Is(err, ErrTransient)` is retryable.
**Options:** (A) bounded automatic retry with backoff for idempotent operations and explicit no-retry for ambiguous rotate. (B) no automatic retry; expose typed transient errors and document caller retry. (C) retry everything with an idempotency token.
**Recommendation:** **(A)** with a documented per-operation policy and a bounded budget; add `ErrTransient`/`Retry-After` handling.

### Q10. Are KEK versions permanent, and is per-version retirement needed?
**Context:** Lazy rewrap leaves old versions in the store/server forever; there is no current-version query, list or retirement API. Destroying a KEK destroys all versions.
**Why it shapes work:** ARCH-05 and storage/compliance requirements depend on it; a retirement API affects the store and adapter contracts.
**Options:** (A) versions are permanent; document it. (B) add `CurrentKEKVersion`/`ListKEKVersions` and a safe `RetireKEKVersion`. (C) delegate version lifecycle to the backend (OpenBao min_decryption_version) and expose a pass-through.
**Recommendation:** **(B)** before v1 if storage/compliance matters; otherwise **(A)** with explicit docs.

### Q11. Does the library emit telemetry, or stay silent?
**Context:** There are no logger/metrics/tracer hooks and no `Close`; operators must wrap every call. A library that takes an OTel dependency burdens consumers; a totally silent one is hard to operate.
**Why it shapes work:** OPS-02 and the `KeyManager` interface/options design depend on it.
**Options:** (A) optional small hooks (`*slog.Logger`, `Observer` events, optional OTel injection) and `Close`. (B) direct OTel dependency. (C) stay silent; document a decorator pattern.
**Recommendation:** **(A)**; it is additive and keeps the core dependency-light.

### Q12. How should root-key files be encoded?
**Context:** `RootKeyFile` currently auto-detects hex, four base64 variants and raw bytes; a truncated hex key or arbitrary 42-byte text is accepted as a different key. This is a data-loss hazard and makes zeroization harder.
**Why it shapes work:** SEC-05 and the config API depend on it; strict decoding is a breaking change for deployments relying on auto-detection.
**Options:** (A) explicit `RootKeyEncoding` (hex/base64/raw) with strict decoders. (B) raw bytes only. (C) keep auto-detection but reject ambiguity/whitespace/truncation.
**Recommendation:** **(A)** with strict decoding; add a migration note and corruption tests.

### Q13. Should `KeyManager` be a concrete struct, an interface, or an opaque handle?
**Context:** `Open` returns `*KeyManager`; redaction currently works only on the pointer, and value copies leak. Returning an interface or an opaque value handle would make copies safe by construction.
**Why it shapes work:** SEC-03/04 and the API ergonomics depend on it; changing the return type is breaking.
**Options:** (A) return `keymanager.KeyManager` (interface) from `Open`. (B) keep concrete types but make redaction value-safe and document copy semantics. (C) keep pointer-only and add `noCopy`/documentation.
**Recommendation:** **(B)** for ergonomics (callers may want concrete methods) with value-safe redaction; **(A)** if preventing copies is more important.

### Q14. Should CI use mise as the single source of truth?
**Context:** `mise.toml` pins Go/golangci-lint/gofumpt/sqlc, but CI hardcodes gofumpt `v0.12.0` and golangci-lint `v2.15.0` and reads Go from `go.mod`; `mise run check` is not used in CI. A one-sided bump can make local and CI disagree.
**Why it shapes work:** DX-02/MAINT-03 and the release process depend on it; a mise-action change is low-risk but affects every workflow.
**Options:** (A) use `jdx/mise-action` and `mise run check` in CI. (B) keep inline pins but add a CI drift assertion against `mise.toml`. (C) keep duplication and document it.
**Recommendation:** **(A)**; it makes the declared single source true. Keep `go-version-file: go.mod` only if the module floor intentionally differs from the dev toolchain.
